# CLAUDE.md

Закрытый мессенджер для узкого круга (3–5 человек). Главное — голосовые и видеозвонки с E2E-шифрованием и минимальной задержкой. Текст вторичен. Регистрация только по инвайтам админа. Один сервер, который можно быстро заменить.

Общение с разработчиком: по-русски, коротко, без воды. Идентификаторы, коммиты и комментарии в коде — на английском.

## 1. Принципы (нарушать нельзя)

1. **Сервер одноразовый.** Всё критичное живёт на клиентах: ключи, сертификаты, история, исходящая очередь. Потеря сервера = потеря максимум недоставленных сообщений за ≤24 ч, и то только если у отправителя тоже умерло устройство.
2. **Сервер не видит содержимого.** Только зашифрованные блобы, публичные ключи и метаданные маршрутизации.
3. **Медиа идёт P2P.** TURN — только fallback.
4. **Криптографию не изобретаем.** Только стандартные примитивы из проверенных библиотек: Ed25519, X25519, HKDF-SHA256, XChaCha20-Poly1305. Подписываем канонические байты, никогда не JSON.
5. **Сервер ничего не пишет на диск и ничего не хранит дольше 24 ч.** Ящики только в RAM. Защита заложена в архитектуре, а не в механизмах самоуничтожения (их не делаем). Единственное исключение — вложения (фото): E2E-зашифрованные файлы на диске, поверх зашифрованные ключом, который живёт только в RAM relay; каталог стирается при старте.

### Запрещено

- Логировать plaintext, ключи, SDP целиком и токены. В логах сервера не должно быть IP и идентификаторов пользователей.
- Вшивать в клиент TURN-секрет, FCM/APNs-ключи и любые другие серверные секреты.
- Подключать аналитику, крашрепортеры и SDK, которые шлют данные третьим сторонам. FCM — только для пустых wake-up пушей.
- Менять формат протокола без обновления `protocol/` и тест-векторов.

## 2. Компоненты и границы доверия

```
            ┌───────────── доверенное ─────────────┐
 Админ ──►  корневой ключ Ed25519 (офлайн)          │
            │  подписывает: сертификаты, манифест,  │
            │  релизы приложения                    │
            └───────────────────────────────────────┘
                 │ публичная часть вшита в клиент
                 ▼
 Клиент A ◄════ P2P медиа (DTLS-SRTP) ════► Клиент B
    │  E2E-блобы, подписанный сигналинг        │
    └──────────► relay (недоверенный) ◄────────┘
                 coturn (недоверенный, fallback)
                 Nostr-релеи (недоверенные, fallback-сигналинг)
```

- **Клиент** — единственный источник правды: проверяет сертификаты, манифест, подписи SDP и подлинность сервера.
- **Relay** — тупой почтальон: аутентифицирует по сертификату, складывает блобы, пересылает сигналинг, выдаёт TURN-креды, будит push'ем. Скомпрометированный relay может задерживать и терять сообщения, видеть метаданные («кто кому»), но не может читать сообщения и выдавать себя за пользователей.
- **coturn, STUN, Nostr, FCM/APNs** — недоверенный транспорт.

### Релиз приложения

1. Поднять `version: x.y.z+build` в `app/pubspec.yaml` (build только растёт — по нему клиент решает, что версия новее).
2. `tools\build-release.ps1` — кладёт в сборку последний подписанный `manifest.bin` из папки админа, собирает APK и установщик.
3. botatoadmin → «Релиз и выкатка» → пароль → «Подписать релиз и выкатить»: `releases/release.bin` (подписан корневым ключом, `protocol/README.md` §3b) + файлы в папке админа, затем Ansible выкладывает их в `/opt/botato/releases`, Caddy раздаёт как `/releases/*`.
Android — два APK: arm64 и 32-битный ARM (`android-arm`, armeabi-v7a: у части бюджетных Samsung, например A40, 32-битная ОС на 64-битном процессоре); клиент берёт файл своей архитектуры. Постоянные ссылки: `botato-latest.apk` (arm64), `botato-latest-arm32.apk`, `botato-latest.exe`. minSdk 24 (Android 7); всё, что новее, — проверками версии в одном APK. Самообновление на Android 12+ — без окна подтверждения (сессия `PackageInstaller`, `USER_ACTION_NOT_REQUIRED`; первое обновление после установки через adb/браузер спросит один раз), ниже — системный установщик; после обновления — уведомление «открыть».

4. Клиенты (Android, Windows) раз в 6 ч и при старте берут `release.bin`, проверяют подпись и build, предлагают обновиться; скачанный файл ставится только при совпадении размера и SHA-256. Сервер может задержать обновление, но не подменить.

После удаления устройства botatoadmin сам подписывает манифест с отзывом и выкатывает его (`--tags manifest`).

## 6. Протокол

Детали, байтовые раскладки и тест-векторы — в `protocol/README.md`. Здесь только суть.

### Кодирование

- Всё подписываемое — каноническая бинарная структура: big-endian, строки `u16 длина + UTF-8`, первый байт — версия формата, лишние байты = ошибка.
- Подпись всегда `Ed25519(ctx || body)`, где `ctx` — строка доменного разделения (`botato/v1/cert\0`, `botato/v1/manifest\0`, `botato/v1/auth-server\0`, `botato/v1/auth-client\0`, …). Подписанный объект = `body || sig`.
- WebSocket-фреймы — JSON с полем `t`. Они не подписываются: всё, что требует целостности, подписано внутри блобов. Бинарные поля — base64, идентификаторы — hex.
- `user_id`, `device_id` и `id` сообщения — случайные 128 бит, одно пространство имён.

### Идентичность и устройства

- Админ держит **корневой ключ Ed25519**: офлайн, зашифрован, минимум две резервные копии. Публичная часть вшита в клиент. Потеря ключа = нельзя выдавать инвайты и переезжать на новый сервер.
- Устройство при первом запуске генерирует свои пары ключей (Ed25519 для подписи, X25519 для шифрования) и показывает публичную часть QR-кодом.
- **Сертификат — один на пользователя** (подписан админом):
  `{user_id, name, issued_at, expires_at, devices: [{device_id, sign_pub, enc_pub}]}` (до 8 устройств).
- Добавить устройство = админ перевыпускает сертификат с расширенным списком. Среди валидных сертификатов одного `user_id` действует самый свежий по `issued_at`.
- Убрать устройство = перевыпустить сертификат без него **и** добавить `device_id` в `revoked` манифеста (иначе старый сертификат живёт до `expires_at`).
- Клиент принимает сообщения, сигналинг и звонки только от устройств из валидного неотозванного сертификата. Проверка локальная.
- Relay аутентифицирует **устройство**. Новое подключение того же `device_id` вытесняет старое; разные устройства пользователя подключены одновременно.
- Новое устройство начинает с пустой историей, старая переписка не синхронизируется.

### Подключение устройства (онбординг)

1. Приложение генерирует ключи и показывает **запрос** `botato-req1:…` — QR и текст.
2. Запрос уходит админу по любому каналу. Админ и пользователь **сверяют отпечаток** (20 цифр) голосом или лично: канал недоверенный, ключи в запросе могут подменить.
3. `admin enroll <запрос>` (новый пользователь) или `admin enroll <запрос> --user <user_id>` (ещё одно устройство) → сертификат `botato-cert1:…` (текст, `--qr` для QR в терминале). Возвращается по любому каналу — он подписан.
4. Приложение импортирует сертификат и подключается к серверу из встроенного манифеста. Адрес сервера пользователь не вводит.

Перевыпущенный сертификат (новое устройство, `admin renew`) достаточно импортировать на одно устройство: остальные получат его через справочник.

### Справочник сертификатов

- Relay держит в RAM последний сертификат каждого пользователя, который подключался (клиент предъявляет его при auth), и отдаёт весь справочник по запросу.
- Клиент проверяет подпись админа и хранит у себя самый свежий сертификат каждого контакта. Подделать сертификат сервер не может, может только не отдать свежий: тогда клиент работает со старым до его истечения или до отзыва в манифесте.

### Манифест

```
{ version (монотонный), issued_at,
  servers: [{ url, ip_fallback, server_pub }],
  stun: [...], nostr_relays: [...],
  revoked: [user_id | device_id, ...] }
```

- Клиент принимает манифест только с валидной подписью админа и `version` больше текущей.
- Каналы распространения (при недоступности сервера клиент проверяет все): встроенный в сборку, `GET /manifest` на сервере, replaceable-событие в Nostr, статическое зеркало (Pages или gist).
- Relay читает манифест из файла (перечитывает при изменении) ради `GET /manifest` и списка отзыва. Отозванных отключает сразу, их ящики стирает.

### Аутентификация (WS `/ws`)

```
C→S hello     {v, nonce: cn}
S→C challenge {nonce: sn, server_pub, sig: Sign(server, ctx || cn || sn)}
    клиент: server_pub ∈ manifest.servers и подпись верна, иначе рвёт соединение
C→S auth      {cert, device_id, sig: Sign(device, ctx || sn || server_pub || cn)}
S→C ready     {user_id, device_id}
```

Клиент проверяет сервер **до** того, как раскрыть свой сертификат. `server_pub` в подписи клиента не даёт переиграть её на другом сервере. На рукопожатие даётся 10 с.

### Фреймы после `ready`

| C→S | S→C | Смысл |
|---|---|---|
| `send {to, id, blob}` | `stored {id}` | положить в ящик устройства `to`; повтор того же `id` идемпотентен |
| | `deliver {id, from, blob}` | выдача из ящика (онлайн — сразу, иначе при подключении) |
| `ack {id}` | — | устройство подтвердило, сервер удаляет |
| `signal {to, blob}` | `signaled {to, online}` | сигналинг звонка на устройство `to`, в ящик не пишется. Устройство офлайн → wake-up push + удержание в RAM ≤60 с |
| | `signal {from, blob}` | входящий сигналинг |
| `directory {}` | `directory {certs}` | справочник сертификатов |
| `turn {}` | `turn {urls, username, credential, ttl}` | TURN-креды на 2 ч |
| `push_token {platform, token}` | `ok` | регистрация push-токена (только RAM, клиент шлёт при каждом подключении) |
| `upload {id, data}` | `uploaded {id}` | вложение ≤2 МиБ (зашифровано случайным ключом из сообщения), хранится 24 ч |
| `download {id}` | `file {id, data}` | любое аутентифицированное устройство, знающее `id`; иначе `error not_found` |
| `presence {devices}` | `presence {online}` | какие из устройств сейчас подключены (для статуса «в сети») |
| | `error {ref, id?, code}` | `bad_frame`, `too_large`, `quota`, `rate_limited`, `revoked`, `unavailable`, `internal`, `not_found` |

`to`/`from` — это `device_id`. `from` от сервера — только подсказка: настоящий отправитель подписан внутри блоба. Push-токен, ящик и удержание сигналов — на устройство.

HTTP: `GET /manifest`, `GET /healthz` (наружу Caddy отдаёт только `/ws`, `/manifest`, `/releases/*`). Всё, что требует аутентификации, идёт по WS.

Close-коды: `4000` протокол, `4001` auth, `4002` вытеснен новым подключением, `4003` отозван, `4004` таймаут auth.

Лимиты: блоб ≤64 КБ, вложение ≤2 МиБ; квоты на отправителя и получателя (число и байты); rate limit на соединение (token bucket); ограничение числа одновременных незавершённых рукопожатий.

## 7. Сообщения

1. Отправитель шифрует отдельную копию на каждое устройство получателя и на свои остальные устройства: эфемерный X25519 → HKDF → XChaCha20-Poly1305. Внутри шифротекста — подпись устройства-отправителя. У всех копий общий логический `msg_id` внутри шифротекста, у каждой копии свой транспортный `id`.
2. Кладёт копии в **локальный outbox** и отправляет на сервер.
3. Сервер хранит их в RAM с `expires_at = now + 24h` и раз в минуту удаляет просроченное.
4. Устройство получателя забирает копию → `ack` серверу → дедупликация по `msg_id` → **E2E-квитанция** отправителю (обычное маленькое сообщение).
5. Отправитель удаляет копию из outbox **только по E2E-квитанции** от этого устройства, а не по `stored`. Сообщение считается доставленным, когда квитанцию прислало хотя бы одно устройство получателя.
6. Outbox переотправляет автоматически: при каждом подключении к relay (в том числе к новому серверу). Нет квитанции за 24 ч с момента отправки → копия удаляется, сообщение помечается «не доставлено». Ручного повтора нет.

Из-за шагов 5–6 смерть или перезапуск relay не теряет сообщения в пределах 24 ч: outbox переотправляется, дубликаты отсекаются по `msg_id`.

Реализация (форматы — `protocol/README.md` §6.2): логика целиком в Rust (`app/rust/src/client`), Dart — только UI. История и outbox — SQLite в папке приложения; тело сообщения зашифровано XChaCha20-Poly1305 ключом из защищённого хранилища ОС (AAD = `msg_id`), метаданные открыты. Квитанция отправляется на каждую копию (и на дубликаты), `ack` серверу — после записи. Сообщение от ещё неизвестного устройства не ack'ается: клиент запрашивает справочник и обрабатывает его после.

Фото (§6.3): отправитель пережимает в Rust (JPEG ≤1600 px; PNG — скриншоты, прозрачность — остаётся PNG ≤2560 px, если влезает в 2 МБ; без метаданных, превью ≤64 px внутри сообщения). «Поделиться → botato» из других приложений (текст, одно или несколько фото): выбор контакта → чат, фото после подтверждения; из просмотра фото — «Поделиться» наружу. На Android галерея отдаёт оригинал: PNG идёт как есть, остальное (JPEG, HEIC) сначала уменьшается системным декодером до 3200 px и превращается в JPEG; шифрует файл случайным ключом, `upload` до копий сообщения на том же соединении и перезаливает при каждом подключении, пока есть недоставленные копии. Получатель скачивает при получении и повторяет на следующих подключениях; через 24 ч от `sent_at` — «фото недоступно». Локально фото лежит в SQLite, зашифрованное тем же ключом, что и история.

Ответы, пересылка, правки, удаление, реакции (§6.2):
- В kind 2 есть `reply` (снимок цитаты ≤200 символов, рисуется даже без оригинала) и `fwd` (имя автора оригинала). Пересылка фото заливает его заново под новым ключом.
- kind 4 — обновление (`edit`/`delete`/`react`) с собственным логическим `id`; идёт через тот же outbox и квитанции, что и сообщения. Правит только автор; удалить у всех может любая сторона — сообщение исчезает без заглушки; реакция — одна на пользователя, любое эмодзи. Сообщение из 1–3 эмодзи рисуется крупно без пузыря.

Контакты и статус:
- Контакт в списке появляется, только когда его добавили по имени из сертификата или по `user_id` (кнопка «Добавить»), либо когда он сам написал или позвонил. Найти можно любого, кто хоть раз подключался с сертификатом.
- Переименование — локальный псевдоним только на этом устройстве, виден везде (список, чат, звонок, уведомления).
- Порядок в списке: по последнему сообщению или моменту добавления контакта — что новее.
- «В сети» — хотя бы одно устройство контакта подключено к relay (`presence`, опрос раз в 15 с). Телефон со свёрнутым приложением показывается «не в сети», но звонки и сообщения доходят через push.

Прямой секретности у сообщений пока нет: план — Double Ratchet (§12, этап 10).

## 8. Звонки

- Сигналинг: основной канал — WS relay, fallback — Nostr-релеи (события зашифрованы на ключ получателя). Сигналы — E2E-конверты kind 1 (`protocol/README.md` §6.1): подпись устройства в конверте аутентифицирует SDP, WebRTC сверяет DTLS-сертификат с fingerprint в этом SDP — MITM на сигналинге не проходит. Опционально — SAS-код на экране.
- ICE: STUN из манифеста + свой TURN (UDP 3478, TLS 5349), `iceTransportPolicy: all`, прямой путь в приоритете. Звонок через наш TURN проверен вживую. На экране звонка — статистика (маршрут host/srflx/relay, RTT, битрейты, fps, потери, кодер/декодер и во что упирается качество).
- В каждом звонке согласуются аудио- и видео-трансиверы `sendrecv`: камера, демонстрация экрана, смена устройств и аудио-режимы — через `replaceTrack`/`setParameters` без пересогласования; `media`-сигнал говорит собеседнику, что показывать.
- Смена сети (Wi-Fi ↔ LTE, VPN): ICE `disconnected` сначала ждёт 1,5 с (сброс собеседника доходит, сеть часто восстанавливается сама; Android видит закрытое соединение раньше, чем приходит `hangup`), `failed` — сразу; затем relay-клиент переподключается, звонящий шлёт `reoffer` (ICE restart), повторяет тот же `reoffer` до ответа, 40 с на восстановление. Сигналы обрабатываются строго по очереди. Проверено вживую (VPN вкл/выкл в звонке): звук возвращается за ~2–3 с.
  - ICE restart в flutter_webrtc: `pc.restartIce()` + `createOffer({'mandatory': {'IceRestart': true}})`. Опции offer на верхнем уровне (`{'iceRestart': true}`) плагин на Android/Windows молча игнорирует — новых кандидатов тогда нет.
  - Пока идёт перезапуск, свои новые кандидаты придерживаются до отправки `reoffer`/`reanswer`, чужие — копятся до применения ответа; при повторе `reoffer` кандидаты отправляются заново.
  - Лог звонка (`[call …]` в `flutter logs` / logcat, тег `flutter`): состояния ICE, типы кандидатов (без адресов), время восстановления, сводка ICE при отказе.
- Мультидевайс: вызов уходит на все устройства пользователя. Ответило одно → звонящий шлёт остальным `hangup answered_elsewhere`.
- Видео: кодек выбирает звонящий (настройка «Видеокодек», поле `vcodec` в `offer`), принимающий ставит его первым в ответе, остальные остаются запасными. На обоих тестовых устройствах есть VP8, VP9, H264, H265, AV1; для игр с минимальной задержкой — H264 (или H265 при аппаратном кодировании). Демонстрация экрана: 30/60 fps, `maintain-framerate`, потолок 8/12 Мбит/с; камера — balanced, 2,5 Мбит/с.
- Интерфейс: звонок можно свернуть («Назад», «Свернуть», «Чат») — сверху приложения плашка «вернуться к звонку». При видео собеседника кнопки прячутся через 4 с, тап возвращает; на ПК — полный экран (Esc), на Android — скрытие системных панелей. Экран гаснет у уха, только когда звук идёт в разговорный динамик.
- Звуки свои (`tools/gen-sounds.py` синтезирует WAV в `app/assets/sounds` и `res/raw`): гудки дозвона, входящий, сброс, переподключение, сообщение, старт трансляции. Android: тоны звонка играет `Sounds.kt` как голосовой поток (идут туда же, куда звонок), входящий и сообщение — звуки каналов уведомлений (`incoming_calls_v2`, `messages_v2`). ПК: `lib/sounds.dart` (audioplayers), уведомления Windows без своего звука; «не беспокоить» глушит и звуки.
- Из SDP убирается RTP-расширение `video-orientation` (отправитель сам поворачивает кадры: Windows-рендерер его не всегда учитывает).
- Android: `CallForegroundService` (типы microphone/camera/mediaProjection) с несмахиваемым CallStyle-уведомлением (микрофон, сброс) — без него Android 14+ отнимает микрофон в фоне. Входящий — CallStyle-уведомление с рингтоном и full-screen поверх экрана блокировки; «Принять» из уведомления — без камеры. Полноэкранный показ на Android 14+ требует разрешения «полноэкранные уведомления», которое у приложений не из Google Play выключено: приложение проверяет его при запуске и в профиле и ведёт в настройки. Активность одна (`singleTask`); перед входящим остановленная активность закрывается, чтобы full-screen intent создал её заново поверх экрана блокировки (движок Flutter общий и переживает это). Поверх экрана блокировки доступен только звонок: «Свернуть», «Чат», «Назад» и уведомление о сообщении во время звонка сначала просят разблокировать телефон (`requestDismissKeyguard`). ПК: входящий поднимает окно на передний план.

### Аудио-режимы (переключаются во время звонка)

| | Голос (по умолчанию) | Чистый звук |
|---|---|---|
| Софтовые AEC / NS / AGC | вкл | выкл |
| Системная обработка (Android HW AEC/NS, iOS voice processing) | вкл | выкл |
| Opus | моно, 48 кбит/с | стерео, 128 кбит/с |
| FEC | вкл | вкл |

- Переключение: новый трек с другими констрейнтами → `sender.replaceTrack()`, битрейт через `setParameters`. Без пересогласования.
- `stereo=1` в fmtp Opus согласовывается сразу при установке звонка, иначе стерео потом не включить. Там же `maxaveragebitrate=128000` — потолок; реальный битрейт режима задаётся `setParameters`. DTX выключен в обоих режимах (его нельзя переключить без пересогласования).
- На ПК микрофон и камера выбираются через `optional: [{sourceId}]`: в Windows-реализации flutter_webrtc `deviceId` в аудио-ограничениях — это устройство *вывода*. Сохранённое, но пропавшее устройство сбрасывается на умолчание.
- В UI предупреждение: «Чистый звук» только в наушниках, иначе будет эхо.
- Android: во время звонка всегда `MODE_IN_COMMUNICATION` (в обоих режимах; `MODE_NORMAL` со «звонковым» источником микрофона давал на Samsung очень тихий звук), вывод выбирается вручную в обоих режимах. Режимы отличаются только обработкой WebRTC, каналами и битрейтом. Источник микрофона фиксируется при старте WebRTC и меняется только перезапуском: по умолчанию `VOICE_COMMUNICATION` (обработка системы, аппаратный AEC, микрофон Bluetooth-гарнитуры), настройка «Микрофон без обработки системы» — `MIC` (`bypassVoiceProcessing`, стерео). Диагностика в логе звонка: `audio state` (режим, устройство, громкости, источник/устройство/эффекты записи) и `audio: mic out/in` (средний уровень, dBFS).
- **Android, умолчания:** «Чистый звук», «Микрофон без обработки системы» вкл (`MIC`, `bypassVoiceProcessing`), «Шумоподавление телефона» выкл (работает только со «звонковым» микрофоном). «Голос» на Android — только эхоподавление WebRTC (шумодав и автоусиление рвали голос); ПК по умолчанию «Голос» с полной обработкой. Замеры на S21 Ultra: «звонковый» источник давал −50…−100 dBFS или сильно обработанный звук, обычный микрофон — ровные −12…−15 dBFS. Цена «Чистого звука»: на громкой связи без наушников у собеседника будет эхо. Проверять звук с двумя устройствами в одной комнате нельзя: звук ходит между колонками и микрофонами по кругу.

## 8a. Язык интерфейса

## 9. ПК (Windows)

- Своя строка заголовка (окно без рамки, по центру), крестик прячет в трей. Меню трея: «Открыть», «Не беспокоить» (без уведомлений, входящий не поднимает окно, но звонит в приложении), «Выход».

## 9a. Push

- Android: FCM data-only с пустым payload («проснись и подключись»). Google видит только сам факт пуша.
- iOS (когда вернёмся к нему): VoIP PushKit → обязательный `reportNewIncomingCall` в CallKit.

## 10. Сервер и инфраструктура

### Что есть на сервере

- В RAM: ящики, удерживаемые сигналы, push-токены, сессии. Перезапуск relay стирает всё, и это безопасно (см. §7).
- На диске: ключ сервера (генерируется relay при первом запуске, Ansible забирает публичную часть), TURN-секрет, FCM/APNs-ключи, конфиги, манифест. Всё это ротируется при переезде. Плюс `/opt/botato/files` — вложения ≤24 ч, зашифрованные ключом из RAM (после рестарта нечитаемы, relay стирает каталог при старте), и `/opt/botato/releases` — только текущий релиз (`release.bin`, APK, установщик) и симлинки `botato-latest.apk` / `botato-latest.exe` для постоянных ссылок.
- Своп выключен (`swapoff -a`, убран из fstab), иначе RAM утекает на диск.
- Логи: relay пишет только ошибки без IP и ID. У Caddy нет `log`-директивы. coturn: `no-stdout-log`, `log-file=/dev/null`. journald: `Storage=volatile`.

### Сеть

nftables: входящие по умолчанию `drop` (молча, без reject), первое правило — `ct state established,related accept`. Исходящие открыты (FCM, APNs, Nostr, apt).

| Порт | Что | Доступ |
|---|---|---|
| 443/tcp | Caddy → relay (`/ws`, `/manifest`) | всем |
| 3478/udp+tcp | STUN/TURN | всем |
| 5349/tcp | TURN over TLS | всем |
| 49160–49299/udp | relay-порты coturn | всем |
| 22/tcp | SSH | только IP, прошедшему fwknop-knock (на 30 с, дальше живёт conntrack) |
| 62201/udp | fwknopd (в Debian собран без pcap — обычный UDP-сокет, никогда не отвечает) | всем |
| ICMP | PMTU, ICMPv6 ND | нужное для работы сети |

- coturn: слушает только публичный IP; `denied-peer-ip` на приватные и служебные диапазоны **и собственный публичный IP сервера** (иначе через TURN можно достучаться до локальных сервисов); `no-tcp-relay`, `no-multicast-peers`, `no-cli`; TLS не ниже 1.2 (в coturn 4.10 это умолчание). Relay-порты открыты в файрволе, но coturn пересылает только для аутентифицированных аллокаций. Проверено: чужой пир — ок, 10.0.0.1 и свой IP — 403.
- **Docker обходит nftables** для опубликованных портов. Поэтому coturn работает в `network_mode: host`, relay наружу не публикуется (только внутренняя сеть до Caddy), Caddy публикует только 443. После деплоя проверять сканом снаружи.
- SSH: только ключи, `PasswordAuthentication no`, `PermitRootLogin no`. Ansible стучит в `pre_tasks` (`delegate_to: localhost`). На свежем VPS SSH открыт до конца первого прогона, файрвол включается последним шагом.
- fwknop: ключи в `~/.fwknoprc` (WSL), запись `[vpn-srv]`, `ALLOW_IP source` (без сторонних сервисов определения IP). В `~/.ssh/config` стоит `Match originalhost vpn-srv exec "fwknop ..."` — `ssh vpn-srv` стучит сам. SPA живёт 60 с: часы управляющей машины должны быть синхронизированы (служба w32time в Windows включена).
- Файрвол применяется с автооткатом: `systemd-run` через 180 с удаляет таблицу, если Ansible не смог заново подключиться через knock.

### Текущий сервер

- Провайдер VDSina, KVM, Debian 13. Адрес — в `infra/ansible/inventory.ini`; в код и документацию не хардкодить.
- Домен relay — поддомен личного домена разработчика, DNS в reg.ru (A-запись). Имя задаётся в переменных Ansible и в манифесте, не в коде. TTL записи — 3600 с (минимум у reg.ru). При переезде это не критично: клиент видит несовпадение ключа сервера и берёт новый манифест с зеркал.
- Бутстрап сделан вручную:
  - `vegameta` — администратор, вход по ключу, sudo с паролем;
  - `deploy` — для Ansible и Claude Code, ключ `~/.ssh/deploy_ed25519`, `NOPASSWD` sudo через `/etc/sudoers.d/deploy`;
  - вход по паролю и для root закрыт (`/etc/ssh/sshd_config.d/00-hardening.conf`), пароль root заблокирован.
- Развёрнуто всё (base, docker, app, fwknop, firewall). Снаружи открыты только 443/tcp, 3478/tcp+udp, 5349/tcp, relay-порты coturn; 22 — только после knock (проверено сканом).
- Relay: `wss://<домен>/ws`, TLS от Let's Encrypt через Caddy. Проверка живого relay: `cargo run -p relay --example probe -- wss://<домен>/ws <server_pub>`.
- Инвентарь: `ansible_user=deploy`, `ansible_ssh_private_key_file=~/.ssh/deploy_ed25519`. SSH-алиас в WSL для диагностики — `vpn-srv`. `tcpdump` на сервере нет (для диагностики подключений хватает `/proc/net/nf_conntrack`).
- Нагрузка (1 vCPU, 1 ГБ RAM; временный relay с лимитами 0,4 CPU / 200 МБ): 500 устройств, ~1400 фреймов/с — 13% CPU, ~100 МБ, без ошибок; фото по 2 МБ — загрузка ~20 мс. Наш масштаб (~15 устройств) в сотни раз меньше. Узкое место — память: каждое соединение держит буфер под самый большой прошедший через него фрейм (~0,5 МБ после фото).

### Правила работы агента с сервером

- Изменения на сервере — только через Ansible. Руками — только диагностика.
- Всё, что может отрезать доступ (sshd, nftables, fwknop, sudoers), показывать и подтверждать отдельно. Перед применением держать открытой вторую SSH-сессию, после — проверять вход новым подключением.
- sudoers менять только с проверкой `visudo -c`, sshd — только с `sshd -t` перед reload.
- Резервный доступ — VNC-консоль в панели VDSina. Буфер обмена там ненадёжен, длинные строки (ключи) через неё не вводить.

## 11. Отказ и замена сервера

| Работает без сервера | Не работает |
|---|---|
| Уже идущие P2P-звонки | Звонки через TURN (обрываются, клиент пробует ICE restart напрямую) |
| Новые звонки, если оба в приложении (сигналинг через Nostr, только STUN; работает и когда сервер недоступен только одному) | Входящие на спящий телефон (нет push) |
| Локальная история и outbox | Доставка текста (копится в outbox) |

Клиент: WS упал → backoff-переподключение. После ~1 мин неудач включается режим «сервер недоступен»: сигналинг через Nostr, баннер в UI, опрос всех каналов манифеста раз в несколько минут. Получен новый манифест → подключение → auth → push-токен → переотправка outbox.

Процедура замены (цель ≤15 мин):
1. Новый VPS: **при создании в панели сразу указать SSH-ключ** → `bootstrap.yml` под root → `deploy.yml`.
2. Всё ротируется: новый ключ сервера, новый TURN-секрет, новый FCM/APNs-ключ (старый отозвать). Со старого сервера ничего не переносится.
3. `admin manifest bump` с новым `server_pub` и адресом → публикация во все каналы.
4. Если домен жив — поменять A-запись (TTL 1 ч). Клиент увидит несовпадение ключа, подтянет манифест с зеркал и переподключится.

### 9. Nostr fallback

**Сделано (код, тесты):** `protocol/README.md` §7 + `vectors/nostr.json`; `proto::nostr` (метки пары, события NIP-01, BIP-340 через `k256`); клиент `app/rust/src/client/nostr.rs` (подписка на свои метки, пока приложение активно; сигнал идёт в Nostr, если relay не подключён или ответил `signaled online:false`; дедупликация по хешу конверта на обоих путях; через минуту без сервера — поиск манифеста в Nostr); e2e-тесты с Nostr-релеем в процессе (`client/nostr_tests.rs`); баннер «Сервер недоступен» (Dart); `admin manifest publish-nostr`, botatoadmin публикует манифест в Nostr после каждой выкатки манифеста (ключ Nostr админа — `nostr.key` в папке админа). Пробник релеев: `cargo run -p relay --example nostr_probe -- wss://…` (проверено 2026-09-25: relay.primal.net, nostr.mom, relay.snort.social, offchain.pub, nostr.oxtr.dev, nostr-pub.wellorder.net, nostr.bitcoiner.social — сигналы и манифест ок; relay.damus.io, nos.lol, relay.nostr.band — недоступны отсюда; purplepag.es — запрещает наш kind).

**Проверено вживую (2026-09-25):** манифест v3 с релеями (primal, nostr.mom, snort, offchain, oxtr) выкачен и опубликован в Nostr; ПК отрезан от сервера файрволом — звонки в обе стороны через Nostr, медиа P2P; в том числе когда relay ещё считает ПК онлайн (управляющие сигналы `offer`/`answer`/`hangup`/`reoffer`/`reanswer` всегда дублируются в Nostr). Idle timeout relay снижен до 35 с (выкачено). Баннер «Сервер недоступен» — через 20 с без связи.

**Осталось:** релиз клиента с Nostr; прогон процедуры замены сервера (§11); текст через Nostr — вторым шагом.

План (исходный):

Цель: без нашего сервера (упал, заблокирован, переезд) можно начать звонок, если оба в приложении, и клиенты сами находят новый сервер. Не спасает от «белых списков» операторов (публичные релеи там тоже режутся), спящий телефон не разбудить (push через наш сервер), TURN недоступен (только P2P через STUN).

- **Транспорт, а не безопасность.** По Nostr идёт тот же E2E-конверт (kind 1 сигналы, позже kind 2–4), что и через relay; подлинность — подпись устройства внутри. Nostr-подпись (secp256k1 Schnorr, BIP-340, крейт `k256`) нужна только чтобы релей принял событие: ключ Nostr — случайный на устройство, ни на что не влияет (принцип 4 не нарушается).
- **События:** сигналы звонков — эфемерные (kind 20000–29999, релеи не хранят); текст (вторым шагом) — обычные с NIP-40 `expiration` ≤24 ч. `content` = base64 конверта.
- **Адресация без утечки «кто кому»:** тег `#p`/`#t` = `HMAC-SHA256(k_pair, "botato/v1/nostr-tag\0" || день_UTC)`, где `k_pair` — HKDF от X25519(свой enc, чужой enc) из сертификатов (есть у обоих без обмена). Для релеев — случайные строки, меняются ежедневно; подписка — на теги всех своих пар за вчера/сегодня/завтра (сдвиг часов). IP и время релеи видят.
- **Релеи:** список `nostr_relays` из манифеста, публикация и подписка сразу на 3–5 (дошло хоть через один). Дедупликация по `msg_id`/id сигнала уже есть.
- **Режим «сервер недоступен»:** после ~1 мин неудач подключения к relay — подписка в Nostr, баннер в UI, сигналы звонков дублируются в Nostr; опрос манифеста раз в несколько минут: Nostr (replaceable-событие, kind 30078, `d`=`botato-manifest`), зеркало (Pages/gist), `GET /manifest`. Новый манифест (подпись админа, версия выше) → подключение → push-токен → переотправка outbox. Сервер вернулся — Nostr выключается.
- **Админка:** botatoadmin при выкатке манифеста публикует его в Nostr (и на зеркало).
- **Порядок работ:** `protocol/` (события, вывод тегов, тест-векторы) → Rust-клиент Nostr в `app/rust` (WS к нескольким релеям, NIP-01 `REQ`/`EVENT`, k256) → переключение и баннер в Dart (CallService уже принимает сигналы из любого источника) → публикация манифеста из botatoadmin → живой прогон: погасить relay, позвонить; прогнать процедуру замены сервера (§11) до ≤15 мин.

### 10. Double Ratchet (план)

Цель: прямая секретность и самовосстановление для сообщений (kind 2–4). Реальный выигрыш скромнее, чем у публичных мессенджеров: трафик и так в TLS, relay хранит ≤24 ч, украденное устройство и так читает свою историю; закрывает сценарий «записали трафик → позже добыли ключ устройства». Сигналы звонков остаются на текущей схеме (у медиа уже есть FS через DTLS-SRTP).

- **Библиотека:** vodozemac (Olm: установка сессии через одноразовые ключи + Double Ratchet; Rust, аудит, Apache-2.0). Своей криптографии нет.
- **Пакет ключей устройства:** Olm identity key + fallback key + N одноразовых ключей, подписанные ключом устройства Ed25519 (сертификаты не меняются, перевыпуск не нужен). Новые фреймы: `keys_upload` (клиент при каждом подключении), `keys_claim {device}` → пакет с одним одноразовым ключом (выдаётся один раз). Relay хранит только в RAM; после перезапуска клиенты перезальют, без одноразовых — fallback key.
- **Сессии:** по одной на пару устройств (включая свои), состояние в SQLite под ключом истории. Новое состояние пишется **до** отправки (падение не должно приводить к рассинхрону).
- **Совместимость с outbox:** копия шифруется один раз, переотправляется тот же шифротекст; повтор отсекается по `msg_id`. Сообщения не по порядку — пропущенные ключи с лимитом (~1000 на сессию).
- **Рассинхрон** (переустановка, битая база, одновременный старт сессии): получатель, не сумевший расшифровать, шлёт `session_reset` (v1-конвертом), отправитель заводит новую сессию и переотправляет неподтверждённое. Самое тонкое место — покрыть e2e-тестами.
- **Переход:** версия в конверте — v1 (текущая схема) / v2 (Olm). v2 шлётся устройствам, опубликовавшим пакет ключей, остальным v1; когда все обновятся — v1 только для `session_reset`.
- **Порядок работ:** `protocol/` (пакет ключей, фреймы, конверт v2, тест-векторы) → relay (хранение/выдача пакетов, лимиты) → клиент Rust (vodozemac, хранилище сессий, выбор v1/v2, reset, пропущенные ключи) → e2e-тесты (потери, перестановки, перезапуск relay, переустановка устройства, одновременный старт) → Dart почти не меняется.

## 13. Открытые вопросы

- **Android: проблемы со звуком с микрофона** — разработчик распишет подробности; разобрать до/вместе с этапом 9.
- TURN на 443 для сетей, где открыт только TCP 443 (отели, корпоративный Wi-Fi, часть операторов). Варианты: второй IP или SNI-роутинг перед Caddy. Отложено: пока таких сетей нет.
- «Белые списки» мобильных операторов: в режиме ограничений TCP до сервера доходит, а TLS с нашим SNI глушится — на мобильной сети клиент не подключается (Wi-Fi работает). Варианты: хостинг с адресами из разрешённых, маскировка под разрешённый сайт (обход фильтрации, юр. риски). Отложено, решать отдельно.

## 14. Аудит безопасности (2026-09-25)

Исправлено:
- Android: `MainActivity` экспортирована (лаунчер), и любое приложение могло прислать интент «ответить на звонок» / «показать поверх экрана блокировки». Теперь такие действия выполняются только с токеном процесса, который есть лишь в наших уведомлениях (`IntentGuard`).
- «Поделиться → botato» принимает только `content://` чужих провайдеров: `file://` или URI нашего провайдера позволили бы заставить приложение прочитать свои приватные файлы (база истории).
- Уведомление о сообщении на экране блокировки — «botato: новое сообщение», отправитель и текст только после разблокировки.
- Реакции принимаются только от двух сторон чата.
- Relay: до авторизации сокет может буферизовать сообщение до размера вложения (~2,8 МБ); незавершённых рукопожатий теперь ≤16 (было 64 → до ~180 МБ при лимите контейнера 256 МБ).
- Ansible удаляет старые образы relay.

Проверено и в порядке: логи relay (только ошибки, без IP/ID/токенов; тело ответа FCM не логируется), лог клиента (события без адресов и SDP), подписи/AAD конвертов и файлов, отзыв на relay, обновления (подпись + build + SHA-256), сервер (наружу 443, 3478/5349, 62201/udp; 22 только после knock — проверено снаружи; своп выкл., journald volatile, sshd только ключи, обновления безопасности применены).

`cargo audit`: `rsa` 0.9 (Marvin, RUSTSEC-2023-0071) через `jsonwebtoken` — relay подписывает JWT для FCM локально раз в час, время операций снаружи не наблюдаемо; принято. `ttf-parser` без поддержки — шрифты egui в botatoadmin; принято.

Сделано после аудита (0.1.7):
- Клиент берёт подписанный `GET /manifest` после подключения (не чаще раза в час), принимает только с подписью админа и версией выше текущей, хранит в папке приложения (`manifest.bin`, новее встроенного — главнее). Отзывы и смена сервера доходят без новой сборки; откатить версию relay не может.
- Настройка «Текст в уведомлениях» (профиль): выкл. — только «botato: новое сообщение» (Windows хранит показанные уведомления на диске).
- «Защита экрана» на Android (`FLAG_SECURE`, по умолчанию вкл.): нет чатов в превью «Недавних», нет скриншотов.
- Журнал ошибок `errors.log` в папке приложения: необработанные ошибки Dart, исключения Kotlin, паники Rust (без содержимого сообщений). Профиль → «Журнал ошибок» — посмотреть, скопировать, очистить.

Открыто:
1. `android-release-password.txt` лежит рядом с `android-release.jks` в папке админа открытым текстом — перенести пароль в менеджер паролей. `fcm-service-account.json` тоже открытым текстом (он нужен только для выкатки).
2. Forward secrecy нет (v2: Double Ratchet): утечка ключа устройства раскрывает перехваченный ранее трафик сообщений.

Особенности по дизайну (не баги): снимок цитаты в ответе и имя в «Переслано от» задаёт отправитель; `presence` показывает любому подключённому устройству, кто онлайн; скачанный установщик на Windows запускается из временной папки пользователя (подменить его между проверкой и запуском может только процесс того же пользователя).

## 15. Не делаем и принятые риски

- Устройства без Google-сервисов (Huawei, GrapheneOS и т.п.): в кругу таких нет, поддержку (UnifiedPush, foreground-сервис) не делаем.
- botatoadmin на телефоне: корневой ключ должен быть офлайн, а телефон — самое онлайновое и теряемое устройство. Подпись остаётся на ПК.
- Sealed sender: сервер видит, какие устройства друг другу пишут и звонят, и когда. Для 3–5 человек скрытие отправителя почти ничего не даёт (тайминги и IP всё равно выдают) — не делаем.
- Нет привязки auth к TLS: TLS терминирует Caddy. MITM с валидным TLS-сертификатом на наш домен может ретранслировать рукопожатие и получить то же, что взломанный relay: метаданные и возможность терять сообщения. Содержимое и звонки защищены E2E. Закрыть можно, только терминируя TLS в relay — не стоит сложности.

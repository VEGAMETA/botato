# CLAUDE.md

Закрытый мессенджер для узкого круга (3–5 человек). Главное — голосовые и видеозвонки с E2E-шифрованием и минимальной задержкой. Текст вторичен. Регистрация только по инвайтам админа. Один сервер, который можно быстро заменить.

Общение с разработчиком: по-русски, коротко, без воды. Идентификаторы, коммиты и комментарии в коде — на английском.

## 1. Принципы (нарушать нельзя)

1. **Сервер одноразовый.** Всё критичное живёт на клиентах: ключи, сертификаты, история, исходящая очередь. Потеря сервера = потеря максимум недоставленных сообщений за ≤24 ч, и то только если у отправителя тоже умерло устройство.
2. **Сервер не видит содержимого.** Только зашифрованные блобы, публичные ключи и метаданные маршрутизации.
3. **Медиа идёт P2P.** TURN — только fallback.
4. **Криптографию не изобретаем.** Только стандартные примитивы из проверенных библиотек: Ed25519, X25519, HKDF-SHA256, XChaCha20-Poly1305. Подписываем канонические байты, никогда не JSON.
5. **Сервер ничего не пишет на диск и ничего не хранит дольше 24 ч.** Ящики только в RAM. Защита заложена в архитектуре, а не в механизмах самоуничтожения (их не делаем).

### Запрещено

- Логировать plaintext, ключи, SDP целиком и токены. В логах сервера не должно быть IP и идентификаторов пользователей.
- Вшивать в клиент TURN-секрет, FCM/APNs-ключи и любые другие серверные секреты.
- Подключать аналитику, крашрепортеры и SDK, которые шлют данные третьим сторонам. FCM — только для пустых wake-up пушей.
- Менять формат протокола без обновления `protocol/` и тест-векторов.

## 2. Компоненты и границы доверия

```
            ┌───────────── доверенное ─────────────┐
 Админ ──►  корневой ключ Ed25519 (офлайн)          │
            │  подписывает: сертификаты, манифест   │
            └───────────────────────────────────────┘
                 │ публичная часть вшита в клиент
                 ▼
 Клиент A ◄════ P2P медиа (DTLS-SRTP) ════► Клиент B
    │  E2E-блобы, подписанный сигналинг        │
    └──────────► relay (недоверенный) ◄────────┘
                 coturn (недоверенный, fallback)
                 Nostr-релеи (недоверенные, fallback-сигналинг)
```

- **Клиент** — единственный источник правды: проверяет сертификаты, манифест, подписи SDP и подлинность сервера.
- **Relay** — тупой почтальон: аутентифицирует по сертификату, складывает блобы, пересылает сигналинг, выдаёт TURN-креды, будит push'ем. Скомпрометированный relay может задерживать и терять сообщения, видеть метаданные («кто кому»), но не может читать сообщения и выдавать себя за пользователей.
- **coturn, STUN, Nostr, FCM/APNs** — недоверенный транспорт.

## 6. Протокол

Детали, байтовые раскладки и тест-векторы — в `protocol/README.md`. Здесь только суть.

### Кодирование

- Всё подписываемое — каноническая бинарная структура: big-endian, строки `u16 длина + UTF-8`, первый байт — версия формата, лишние байты = ошибка.
- Подпись всегда `Ed25519(ctx || body)`, где `ctx` — строка доменного разделения (`botato/v1/cert\0`, `botato/v1/manifest\0`, `botato/v1/auth-server\0`, `botato/v1/auth-client\0`, …). Подписанный объект = `body || sig`.
- WebSocket-фреймы — JSON с полем `t`. Они не подписываются: всё, что требует целостности, подписано внутри блобов. Бинарные поля — base64, идентификаторы — hex.
- `user_id`, `device_id` и `id` сообщения — случайные 128 бит, одно пространство имён.

### Идентичность и устройства

- Админ держит **корневой ключ Ed25519**: офлайн, зашифрован, минимум две резервные копии. Публичная часть вшита в клиент. Потеря ключа = нельзя выдавать инвайты и переезжать на новый сервер.
- Устройство при первом запуске генерирует свои пары ключей (Ed25519 для подписи, X25519 для шифрования) и показывает публичную часть QR-кодом.
- **Сертификат — один на пользователя** (подписан админом):
  `{user_id, name, issued_at, expires_at, devices: [{device_id, sign_pub, enc_pub}]}` (до 8 устройств).
- Добавить устройство = админ перевыпускает сертификат с расширенным списком. Среди валидных сертификатов одного `user_id` действует самый свежий по `issued_at`.
- Убрать устройство = перевыпустить сертификат без него **и** добавить `device_id` в `revoked` манифеста (иначе старый сертификат живёт до `expires_at`).
- Клиент принимает сообщения, сигналинг и звонки только от устройств из валидного неотозванного сертификата. Проверка локальная.
- Relay аутентифицирует **устройство**. Новое подключение того же `device_id` вытесняет старое; разные устройства пользователя подключены одновременно.
- Новое устройство начинает с пустой историей, старая переписка не синхронизируется.

### Справочник сертификатов

- Relay держит в RAM последний сертификат каждого пользователя, который подключался (клиент предъявляет его при auth), и отдаёт весь справочник по запросу.
- Клиент проверяет подпись админа и хранит у себя самый свежий сертификат каждого контакта. Подделать сертификат сервер не может, может только не отдать свежий: тогда клиент работает со старым до его истечения или до отзыва в манифесте.

### Манифест

```
{ version (монотонный), issued_at,
  servers: [{ url, ip_fallback, server_pub }],
  stun: [...], nostr_relays: [...],
  revoked: [user_id | device_id, ...] }
```

- Клиент принимает манифест только с валидной подписью админа и `version` больше текущей.
- Каналы распространения (при недоступности сервера клиент проверяет все): встроенный в сборку, `GET /manifest` на сервере, replaceable-событие в Nostr, статическое зеркало (Pages или gist).
- Relay читает манифест из файла (перечитывает при изменении) ради `GET /manifest` и списка отзыва. Отозванных отключает сразу, их ящики стирает.

### Аутентификация (WS `/ws`)

```
C→S hello     {v, nonce: cn}
S→C challenge {nonce: sn, server_pub, sig: Sign(server, ctx || cn || sn)}
    клиент: server_pub ∈ manifest.servers и подпись верна, иначе рвёт соединение
C→S auth      {cert, device_id, sig: Sign(device, ctx || sn || server_pub || cn)}
S→C ready     {user_id, device_id}
```

Клиент проверяет сервер **до** того, как раскрыть свой сертификат. `server_pub` в подписи клиента не даёт переиграть её на другом сервере. На рукопожатие даётся 10 с.

### Фреймы после `ready`

| C→S | S→C | Смысл |
|---|---|---|
| `send {to, id, blob}` | `stored {id}` | положить в ящик устройства `to`; повтор того же `id` идемпотентен |
| | `deliver {id, from, blob}` | выдача из ящика (онлайн — сразу, иначе при подключении) |
| `ack {id}` | — | устройство подтвердило, сервер удаляет |
| `signal {to, blob}` | `signaled {to, online}` | сигналинг звонка на устройство `to`, в ящик не пишется. Устройство офлайн → wake-up push + удержание в RAM ≤60 с |
| | `signal {from, blob}` | входящий сигналинг |
| `directory {}` | `directory {certs}` | справочник сертификатов |
| `turn {}` | `turn {urls, username, credential, ttl}` | TURN-креды на 2 ч |
| `push_token {platform, token}` | `ok` | регистрация push-токена (только RAM, клиент шлёт при каждом подключении) |
| | `error {ref, id?, code}` | `bad_frame`, `too_large`, `quota`, `rate_limited`, `revoked`, `unavailable`, `internal` |

`to`/`from` — это `device_id`. `from` от сервера — только подсказка: настоящий отправитель подписан внутри блоба. Push-токен, ящик и удержание сигналов — на устройство.

HTTP: только `GET /manifest` и `GET /healthz`. Всё, что требует аутентификации, идёт по WS.

Close-коды: `4000` протокол, `4001` auth, `4002` вытеснен новым подключением, `4003` отозван, `4004` таймаут auth.

Лимиты: блоб ≤64 КБ (вложения вне v1); квоты на отправителя и получателя (число и байты); rate limit на соединение (token bucket); ограничение числа одновременных незавершённых рукопожатий.

## 7. Сообщения

1. Отправитель шифрует отдельную копию на каждое устройство получателя и на свои остальные устройства: эфемерный X25519 → HKDF → XChaCha20-Poly1305. Внутри шифротекста — подпись устройства-отправителя. У всех копий общий логический `msg_id` внутри шифротекста, у каждой копии свой транспортный `id`.
2. Кладёт копии в **локальный outbox** и отправляет на сервер.
3. Сервер хранит их в RAM с `expires_at = now + 24h` и раз в минуту удаляет просроченное.
4. Устройство получателя забирает копию → `ack` серверу → дедупликация по `msg_id` → **E2E-квитанция** отправителю (обычное маленькое сообщение).
5. Отправитель удаляет копию из outbox **только по E2E-квитанции** от этого устройства, а не по `stored`. Сообщение считается доставленным, когда квитанцию прислало хотя бы одно устройство получателя.
6. Outbox переотправляет автоматически: при каждом подключении к relay (в том числе к новому серверу). Нет квитанции за 24 ч с момента отправки → копия удаляется, сообщение помечается «не доставлено». Ручного повтора нет.

Из-за шагов 5–6 смерть или перезапуск relay не теряет сообщения в пределах 24 ч: outbox переотправляется, дубликаты отсекаются по `msg_id`.

v2: Double Ratchet (vodozemac, Apache-2.0) ради forward secrecy.

## 8. Звонки

- Сигналинг: основной канал — WS relay, fallback — Nostr-релеи (события зашифрованы на ключ получателя).
- Каждый SDP подписан ключом устройства. DTLS-fingerprint из SDP сверяется с подписью, поэтому MITM на сигналинге не проходит. Опционально — SAS-код на экране.
- ICE: публичные STUN + свой TURN (UDP 3478, TLS 5349), `iceTransportPolicy: all`, прямой путь в приоритете.
- Смена сети (Wi-Fi ↔ LTE) → ICE restart без разрыва звонка.
- Мультидевайс: вызов уходит на все устройства пользователя. Ответило одно → звонящий шлёт остальным `cancel`, они показывают «отвечено на другом устройстве».

### Аудио-режимы (переключаются во время звонка)

| | Голос (по умолчанию) | Чистый звук |
|---|---|---|
| Софтовые AEC / NS / AGC | вкл | выкл |
| Системная обработка (Android HW AEC/NS, iOS voice processing) | вкл | выкл |
| Opus | моно, ~32 кбит/с, DTX вкл | стерео, ~128 кбит/с, DTX выкл |
| FEC | вкл | вкл |

- Переключение: новый трек с другими констрейнтами → `sender.replaceTrack()`, битрейт через `setParameters`. Без пересогласования.
- `stereo=1` в fmtp Opus согласовывается сразу при установке звонка, иначе стерео потом не включить.
- В UI предупреждение: «Чистый звук» только в наушниках, иначе будет эхо.

## 9. Push

- Android: FCM data-only с пустым payload («проснись и подключись»). Google видит только сам факт пуша.
- iOS: VoIP PushKit → обязательный `reportNewIncomingCall` в CallKit.
- Десктоп: без push, фоновое WS-соединение.
- Relay пушит офлайн-получателю при новом сообщении (не чаще раза в 30 с) и при сигнале (не чаще раза в 5 с).

## 10. Сервер и инфраструктура

### Что есть на сервере

- В RAM: ящики, удерживаемые сигналы, push-токены, сессии. Перезапуск relay стирает всё, и это безопасно (см. §7).
- На диске: ключ сервера (генерируется relay при первом запуске, Ansible забирает публичную часть), TURN-секрет, FCM/APNs-ключи, конфиги, манифест. Всё это ротируется при переезде.
- Своп выключен (`swapoff -a`, убран из fstab), иначе RAM утекает на диск.
- Логи: relay пишет только ошибки без IP и ID. У Caddy нет `log`-директивы. coturn: `no-stdout-log`, `log-file=/dev/null`. journald: `Storage=volatile`.

### Сеть

nftables: входящие по умолчанию `drop` (молча, без reject), первое правило — `ct state established,related accept`. Исходящие открыты (FCM, APNs, Nostr, apt).

| Порт | Что | Доступ |
|---|---|---|
| 443/tcp | Caddy → relay (`/ws`, `/manifest`) | всем |
| 3478/udp+tcp | STUN/TURN | всем |
| 5349/tcp | TURN over TLS | всем |
| 49160–49299/udp | relay-порты coturn | всем |
| 22/tcp | SSH | только IP, прошедшему fwknop-knock (на 30 с, дальше живёт conntrack) |
| ICMP | PMTU, ICMPv6 ND | нужное для работы сети |

- coturn: `denied-peer-ip` на приватные диапазоны (10/8, 172.16/12, 192.168/16, 127/8, fc00::/7, ::1), `no-multicast-peers`, `no-cli`, `no-tlsv1`, `no-tlsv1_1`. Relay-порты открыты в файрволе, но coturn пересылает только для аутентифицированных аллокаций.
- **Docker обходит nftables** для опубликованных портов. Поэтому coturn работает в `network_mode: host`, relay наружу не публикуется (только внутренняя сеть до Caddy), Caddy публикует только 443. После деплоя проверять сканом снаружи.
- SSH: только ключи, `PasswordAuthentication no`, `PermitRootLogin no`. Ansible стучит в `pre_tasks` (`delegate_to: localhost`). На свежем VPS SSH открыт до конца первого прогона, файрвол включается последним шагом.

### Текущий сервер

- Провайдер VDSina, KVM, Debian 13. Адрес — в `infra/ansible/inventory.ini`; в код и документацию не хардкодить.
- Бутстрап сделан вручную:
  - `vegameta` — администратор, вход по ключу, sudo с паролем;
  - `deploy` — для Ansible и Claude Code, ключ `~/.ssh/deploy_ed25519`, `NOPASSWD` sudo через `/etc/sudoers.d/deploy`;
  - вход по паролю и для root закрыт (`/etc/ssh/sshd_config.d/00-hardening.conf`), пароль root заблокирован.
- Сейчас наружу слушает только sshd:22. Файрвола, Docker и fwknop пока нет.
- Инвентарь: `ansible_user=deploy`, `ansible_ssh_private_key_file=~/.ssh/deploy_ed25519`. SSH-алиас в WSL для диагностики — `vpn-srv`.

### Правила работы агента с сервером

- Изменения на сервере — только через Ansible. Руками — только диагностика.
- Всё, что может отрезать доступ (sshd, nftables, fwknop, sudoers), показывать и подтверждать отдельно. Перед применением держать открытой вторую SSH-сессию, после — проверять вход новым подключением.
- sudoers менять только с проверкой `visudo -c`, sshd — только с `sshd -t` перед reload.
- Резервный доступ — VNC-консоль в панели VDSina. Буфер обмена там ненадёжен, длинные строки (ключи) через неё не вводить.

## 11. Отказ и замена сервера

| Работает без сервера | Не работает |
|---|---|
| Уже идущие P2P-звонки | Звонки через TURN (обрываются, клиент пробует ICE restart напрямую) |
| Новые звонки, если оба в приложении (сигналинг через Nostr, только STUN) | Входящие на спящий телефон (нет push) |
| Локальная история и outbox | Доставка текста (копится в outbox) |

Клиент: WS упал → backoff-переподключение. После ~1 мин неудач включается режим «сервер недоступен»: сигналинг через Nostr, баннер в UI, опрос всех каналов манифеста раз в несколько минут. Получен новый манифест → подключение → auth → push-токен → переотправка outbox.

Процедура замены (цель ≤15 мин):
1. Новый VPS: **при создании в панели сразу указать SSH-ключ** → `bootstrap.yml` под root → `deploy.yml`.
2. Всё ротируется: новый ключ сервера, новый TURN-секрет, новый FCM/APNs-ключ (старый отозвать). Со старого сервера ничего не переносится.
3. `admin manifest bump` с новым `server_pub` и адресом → публикация во все каналы.
4. Если домен жив — поменять A-запись (TTL 60 с). Клиент увидит несовпадение ключа, подтянет манифест с зеркал и переподключится.

## 12. Этапы

1. `protocol/` + `crates/proto`: форматы сертификата, манифеста, auth; тест-векторы.
2. `server/`: auth, mailbox, signaling, TURN-креды; интеграционные тесты через настоящий WS.
3. `tools/admin`: корневой ключ, сертификаты, манифест, отзыв.
4. `infra/`: Dockerfile, compose (Caddy + relay + coturn), `bootstrap.yml`, `deploy.yml`. Базовая роль: удалить `qemu-guest-agent` и `haveged`, замаскировать `systemd-ssh-generator` (`/etc/systemd/system-generators/systemd-ssh-generator → /dev/null`), выключить своп, journald volatile, unattended-upgrades только для security. Затем Docker, nftables, fwknop — последним. Проверка портов сканом снаружи.
5. Клиент: ключи, QR, подключение к relay, P2P-звонок с подписанным SDP и проверкой fingerprint.
6. Текст по схеме outbox и квитанций.
7. Аудио-режимы.
8. Push + CallKit.
9. Fallback через Nostr, сценарий отказа сервера, прогон процедуры замены вживую.

## 13. Открытые вопросы

- TURN на 443 для сетей, где открыт только TCP 443 (отели, корпоративный Wi-Fi, часть операторов). Варианты: второй IP или SNI-роутинг перед Caddy. Отложено: пока таких сетей нет.

## 14. Не делаем и принятые риски

- Устройства без Google-сервисов (Huawei, GrapheneOS и т.п.): в кругу таких нет, поддержку (UnifiedPush, foreground-сервис) не делаем.
- Sealed sender: сервер видит, какие устройства друг другу пишут и звонят, и когда. Для 3–5 человек скрытие отправителя почти ничего не даёт (тайминги и IP всё равно выдают) — не делаем.
- Нет привязки auth к TLS: TLS терминирует Caddy. MITM с валидным TLS-сертификатом на наш домен может ретранслировать рукопожатие и получить то же, что взломанный relay: метаданные и возможность терять сообщения. Содержимое и звонки защищены E2E. Закрыть можно, только терминируя TLS в relay — не стоит сложности.
